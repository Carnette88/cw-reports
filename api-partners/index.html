HubSpot Integration Status

The tagging system exists but isn't disciplined.

HubSpot ships two boolean properties on the Company object — api_interested and api_qualified — that were created at some point to act as the program flag for API partners. Both are still in use, but neither matches the reality of who is in the API program at any given stage.

The gap between 49 HubSpot-flagged records and 15 actual credentialed accounts is the disconnect. Today this dashboard's source of truth is a hand-maintained YAML registry plus the May 11, 2026 API Partner Audit memo — not HubSpot. That's fragile and won't scale as the BD team starts actively hunting API partners.

Recommendation — unify the schema, mandate the discipline.

  • Replace the two booleans with one stage field. Propose a new Company property api_partner_stage as an enum: Discovery → In Discussion → Testing → Live → Dormant → Idle Credentials. That mirrors the dashboard and gives BD a single source of truth for "what stage is this partner at."
  • Mandate the field on every API-program record. Required when a partner is added to the program, updated when the partner advances or stalls. BD owns updating it; Cory + Cassie's Pod can audit weekly.
  • Retire api_interested / api_qualified. Backfill the 49 records into the new enum where they actually belong, then hide the legacy booleans to prevent re-pollution.
  • Flip the data flow. Once the discipline holds, HubSpot becomes the registry. This dashboard reads from HubSpot directly, and the YAML retires. Then a partner advancing in HubSpot shows on the dashboard automatically.
Why this matters: Without a clean tag, the BD team can't be measured on API pipeline progression and Cory + Cassie's Pod lose visibility on partners that show interest but stall. With the tag in place, the funnel from "first conversation" to "credentialed and producing" becomes a real reportable metric.
Methodology. Live = service account actively submitting YTD. Dormant = was live in 2025, ≤ a handful of subs YTD 2026. Idle = API service account provisioned but no production history — deprovision-or-reactivate candidates. Submissions are NB only (transaction_id=0, status NOT IN (0,7), any LOB quote-request flag). Quoted = status IN (1,3,10). Bound = status=1. GWP from dw_reader.policy_transaction_premium filtered to New Business, joined on submission_id. Setup/Testing partners appear in the Prospects & Dev Work section above with their pipeline status (Testing / In Discussion / Discovery / Parked) — they have no service account yet and so produce no Metabase signal.
